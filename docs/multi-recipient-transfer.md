# 多设备发送与局域网连接

## Windows 0.2.2 当前实现

一次选中多个设备时，后台只枚举一次所选文件夹，共享文件清单、排除项及块摘要准备。每个接收设备拥有独立传输 ID、接收确认、进度、暂停、继续、取消与失败结果。全局最多同时进行四路发送，其他目标排队；一次可选择 1–32 台设备，后台发送队列最多 128 个目标。某台设备拒绝、身份校验失败或取消，不影响其他接收方。

新设备通过 `chunks-v1` 能力协商使用共享 `ChunkTransfer` / `ChunkStore` 引擎；旧设备继续走原有逐文件 TLS 流。新引擎先生成稳定内容清单，接收端按需拉取 SHA-256 块，重新打开缓存时逐块验证，最终验证全部内容再提交。默认块为 1 MiB，清单大小需要时增至最多 8 MiB。文件和更新包共享这一下载、存储与验证实现；更新额外保留发行签名、ZIP 内容校验与安装步骤。

## 暂停与恢复

发送任务在本机 `recoverable-sends.json` 中保存传输 ID、批次 ID、接收方指纹、源路径、排除项和描述。暂停或后台退出保留任务；重启后以暂停状态显示，用户明确继续才重新连接，不自动重发。恢复时重新枚举源内容并校验设备身份，接收方仍重新执行许可检查。源内容改变会得到不同内容清单，不混用旧块。

接收端将未完成内容保留在收件目录内的私有 `.boardcast-resume-*` 目录，以发送者身份和内容标识区分；恢复只复用重新通过摘要检查的块。同一传输已提交后的完成回执可在重试时验证并复用，避免因最后确认丢失而生成重复收件。恢复记录最多 128 项，重启时忽略超过七天的记录；后续分块接收会清理超过七天且未活动的残留接收缓存。这不是跨文件、跨发送者的全盘去重。

显式取消移除本机恢复任务；完成或拒绝也不再提供继续入口。远端残留缓存按上述清理规则处理，取消发送不表示已经删除其他设备上获得的字节。旧设备没有分块缓存能力，继续该任务需要从头传输。

## 有条件的 P2P 分发

P2P 是同批已批准接收者之间的补充来源，不是任何文件都启用的默认传输模式。原发送者仍提供权威清单，并保持直接 mTLS 传输路径。候选来自该批次已经接受传输的设备；旁观设备不能通过广播发现获得文件名、清单或读取授权。

当前 `ChunkPeerPolicy` 使用以下保守策略，阈值是工程初值，尚未依据实体 LAN 基准调优：

- 载荷至少 64 MiB，且原发送者同时服务至少两名活动接收者，才尝试普通文件的同批中继。
- 先测量至少两个直接来源块；候选至少报告两个块的已验证数据，仍有至少 8 MiB 未完成且当前块至少 256 KiB，才允许受限试探。
- 同一来源最多一个块请求在途，全局最多一个未经证明的来源试探；普通文件最多三个块工作者，并持续保留原来源请求。
- 候选实际成功速度和加权速度均达到当前原来源速度的 80% 才继续使用。过慢、缺块、超时或失败来源退避，从 30 秒递增到最多五分钟；试探超时依据原来源速度限制在 2–10 秒。
- 中继离线或块校验失败时回到原发送者；不因中继存在就强制分流。

中继连接同样绑定设备证书指纹。原发送者用设备私钥签发授权，绑定唯一 `GrantId`、随机 `BatchId`、内容 ID、接收者指纹和有效期；票据最长有效两小时。接收设备只读取同一授权内容中已经通过 SHA-256 的块，不能指定任意本机路径。每次块请求检查授权及具体票据撤销记录；新中继会话回询原发送者，持续连接每 30 秒重新确认，无法确认即拒绝后续请求。未完成连接结束会移除该接收者并向其余来源发送受认证的票据撤销通知。推送失败时，既有会话可在当前至多 30 秒的授权租期内继续请求，已经开始的块也可能完成；不能把取消描述为即时远端撤回。每台设备最多同时服务两路中继。传输完成不等于内容向所有附近设备公开。当前不提供公网 tracker、DHT、打洞或云中继。

更新包是相同块引擎的另一种文件载荷：仅用户所选版本、同一发行包 SHA-256/大小/块清单的已验证来源可共同参与。选定来源立即开始，最多两个额外候选按需连接；恢复后的剩余内容至少 64 MiB，且实测选定来源速度低于 32 MiB/s 时才进行条件试探，主来源故障时可另行尝试同包副本。详细流程见[局域网版本更新](peer-updates.md)。

这套策略避免无条件 P2P，但不能保证总是更快：多个设备可能共享同一个 Wi-Fi 信道、慢盘或交换机出口。Steam 官方分发资料、IETF 和其他权威依据，以及哪些数值属于本项目决策，见[P2P 分发研究](p2p-distribution-research.md)。

## 暂缓组播与其他传输协议

UDP 广播仅用于发现设备，文件数据仍经 mTLS。文件组播、群组密钥交换及 QUIC 本轮不实现。可靠组播须同时解决丢包修复、反馈抑制、拥塞控制和授权接收者密钥管理，不能直接替换现有 TLS。IETF [NORM（RFC 5740）](https://www.rfc-editor.org/rfc/rfc5740.html)、[FLUTE（RFC 6726）](https://www.rfc-editor.org/rfc/rfc6726.html) 和 Windows [PGM](https://learn.microsoft.com/en-us/windows/win32/winsock/reliable-multicast-programming--pgm-) 描述了相关额外要求。引入这些路径应以实体有线 LAN / Wi-Fi 测量的收益为前提。

## LAN 状态与发现

`settings.lanOnline` 与 `settings.receivingEnabled` 相互独立。断开 LAN 会广播 `goodbye`，停止新的发现、直接 IP 连接和发送，取消尚未开始或等待批准的发送，并拒绝未批准的接收。已接受的文件传输可完成。重新连接主动广播 `announce` 与 `probe`；系统网络恢复也会触发发现。名称、接收开关或版本等设置变化立即发布，不需等下一次 60 秒公告。

发现包没有认证。`goodbye` 只有在现有指纹、来源地址、发现端口和已登记 TCP 端口都对应时才记录 `departureHint`，不删除设备身份、不延长过期时间、也不增加信任。新观察会清除提示；150 秒未见后记录自然过期。真实身份与更新发行包仍分别通过 mTLS 与发行签名验证。

## IPC 与验证边界

- `set-online`：`lanOnline: true/false`，返回最新 snapshot。
- `send-many`：`peers: [...]` 加原有 `paths` 或 `sources`；来源字段不能同时指定。
- 返回 `transfers: [{id, peerFingerprint, peerName}, ...]`，保留 `transferId` 指向首个目标以兼容旧客户端。
- `send` 保持单设备行为，也返回 ticket；进度包含 `queued`、`paused`、`CanResume`、`ReusedBytes` 和 `PeerBytes`。
- `pause / resume / cancel`：使用某一目标的 `transferId`；取消不再保留该目标的恢复入口。

传输测试覆盖本机真实 mTLS、四路并发、独立失败与取消、重启后分块复用、缓存损坏复查、授权越界、实际中继字节及中继失败回退。恢复测试验证 daemon 的任务持久化与暂停/继续 IPC。实际通过数量和本轮结果统一记录在[验证记录](verification.md)。本机回环和人工延迟场景只验证行为，不代表实体 LAN、Wi-Fi 或 macOS 互通已验收，也不构成速度提升承诺。
