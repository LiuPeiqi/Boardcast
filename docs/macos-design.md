# Boardcast macOS 产品与界面设计

Boardcast 的核心是同一局域网内选择内容、选择设备、确认接收与可靠保存。macOS 应延续 Windows 的任务逻辑和身份边界，并采用 Mac 的窗口、菜单栏、Finder 和键盘习惯。后续在 Mac 上的工作先建立可验证的协议与任务模型，再完善发送工作台，最后补齐存储恢复与扩展能力。

本说明以 2026 年 10 月 9 日的仓库为基线，已在「调整设备列表工具栏布局」会话完成后同步到 Windows 0.2.7：设备保持单行，文件信息按实际可用宽度自适应一行或两行；Windows 发行与验证状态见 [验证记录](verification.md) 和 [签名发行说明](signed-release.md)。独立 Swift 应用的 bundle 版本仍为 0.1.0，二者的版本与已实现能力不能直接等同。下文“现状”对应已写入源码的行为，“设计目标”与 P0 至 P3 对应后续本地实现范围。Swift 源码尚未在本次 Windows 环境编译、运行或完成 Windows 与 Mac 的真实互通验收。

## 产品边界

- 仅在局域网内发现和直接传输，不加入账号、云中继、公网发现、打洞或互联网自动降级。
- 优先保证空闲开销低、内存有界、内容正确与失败可解释。速度、内存和唤醒次数由真实设备测量，不从语言或框架名称推断。
- 设备名、备注和分组帮助辨认；TLS 证书指纹识别身份。发现广播和同组关系都不能建立信任。
- 信任设备、授权自动接收与内容规则分别控制。接收文件不授权执行文件、运行 CLI 或发送内容到外部服务。
- 文件和文件夹共用一次性发送流程；保留目录层级和空目录，不扩展成全盘索引或持续同步工具。
- 默认是登录用户的菜单栏应用。关闭窗口继续等待文件，退出应用结束当前用户的服务；不承诺用户注销后仍能接收。

## 当前实现与迁移差距

| 领域 | Windows 基线 | macOS 现状与缺口 |
| --- | --- | --- |
| 窗口与常驻 | WPF 工作台、可收起侧栏、原生托盘、界面与 daemon 分离 | SwiftUI 主窗、Settings 和 MenuBarExtra；关闭最后窗口不退出。主要状态集中在一个 AppModel |
| 内容选择 | 文件和目录加入待发送清单；拖放、统计、排除、移除与说明 | 选中一个设备后打开 NSOpenPanel，直接开始发送；尚无持久发送草稿、拖放清单、排除编辑和多目标选择 |
| 设备 | 多选、备注、分组、搜索、手动 IP、设备详情；原设备名主要在详情中查看 | 单选设备、备注、分组与信任设置；已有分组筛选，尚无文本搜索和手动 IP 界面 |
| 接收确认 | 来件与任务记录展示状态，来件预览前 8 项；当前没有完整清单入口，首页默认接收目录主要通过提示查看，来件卡展示实际目的地 | 主界面内来件卡、摘要、完整指纹、保存路径及接受和拒绝；确认等待 120 秒，缺少完整清单入口与结构化任务历史 |
| 规则 | first-match、设备双授权、内容条件及真实接收路径 | 已独立实现规则引擎和基础编辑器；设备范围、大小限制等模型字段的编辑体验仍需完善 |
| 传输 | chunks-v1、恢复、多目标共享准备、LAN P2P 来源和更新包流程 | TLS 顺序字节流、逐文件 SHA-256、临时批次完成后提交；尚无块缓存、恢复、P2P 与更新 |
| 本机扩展 | 当前用户 IPC、CLI、stdio MCP、显式摘要动作 | 尚无 CLI、MCP 或 LLM 集成 |
| 分发 | Windows 构建与发行验证链路 | SwiftPM 包与通用 app 构建脚本已存在；Mac 编译、签名、公证、权限和干净设备验收待完成 |

macOS 已有 Network.framework 传输、Security 与 CryptoKit 身份、Keychain 私钥、IPv4 子网 UDP 广播、路径检查、分组和规则测试源码。当前传输采用有界 JSON 帧和缓冲，限制并发连接；不应在 UI 扩展时绕开这些限制。

当前发现范围是物理接口的 IPv4 子网；代码排除 utun 与 ppp，没有 IPv6、跨 VLAN 路由或公网域名连接。源码限制与互通细节以 [协议](protocol.md)、[平台研究](platform-research.md)及 [macOS 构建说明](../platforms/macos/README.md)为准。

### 需要先修正的模型问题

当前设置表单直接绑定 model.settings，而接收开关和分组筛选也通过 save 保存同一对象。这使即时操作可能连带提交仍在编辑的其他字段。网络回调虽然使用已成功保存的 activeSettings，界面草稿与即时设置仍缺乏清晰分离。

后续拆成 SettingsDraft、即时偏好与不可变运行设置快照。接收暂停、分组筛选和显示偏好通过独立命令提交；设置窗口有明确的应用和取消。保存失败保留输入并显示字段错误，不能让主界面显示状态与后台实际状态分离。

当前只有全局 busy 和 status 文本，不能表达多个目标或并发来件。先引入发送草稿、任务与事件模型，再铺开新界面，避免每增加一张卡片就复制网络状态。

## Windows UI 设计基线

当前 Windows 界面把发送与传输记录作为主要导航，设置放在侧栏下部，本机名称与局域网状态保持可见。发送页采用文件清单与附近设备并列布局，通过分隔条调整宽度。列表承担内容，工具区承担操作，主发送按钮位置稳定；短时提示浮于内容层，避免固定状态栏持续挤占列表。

Mac 保留这些信息层级与动作关系，尺寸、颜色、字体和控件使用平台原生方案。Windows 的 1040×580 窗口、920×540 最小尺寸、176 宽侧栏、约 1.5:1 两列以及 8 像素圆角属于当前实现参数，不作为 Mac 的逐像素要求。

当日操作精简后的 Windows 源码已将设备工具区稳定为单行“附近设备 / 分组筛选 / 显示数与总数 / 刷新”：分组按钮占据剩余宽度，计数和刷新保持固定位置，长组名省略而不换行。Mac 保留这套信息层级；更窄宽度可采用紧凑菜单，在中文、英文和长组名下检查可达性。

Windows 的设备项继续采用单行：勾选、平台图标、设备名称、必要的状态图标、版本标记。名称占剩余宽度，长名称省略；正常设备不占用状态图标位置。暂停接收、可能离开或离线时显示警示图标及具体原因。平台文字、分组、信任和地址移入帮助提示、辅助名称及设备详情；对端原名在设备详情核查，不新增常驻信息行。分组筛选与信任判断继续使用完整模型，不依赖行内是否显示标签。

灰色标记显示设备当前运行版本；蓝色可点击气泡显示该设备能提供的适用更新版本，帮助提示同时说明当前运行版本。点击蓝色气泡进入更新详情，不自动下载；取消独立“有更新”气泡。缺少版本的旧设备不补造版本号，灰色标签也不表示设备已经是最新版。

文件区的添加、移除、清空、排除与展开清单集中在顶部工具区。空清单隐藏顶部添加与清空，只留下可点击的箭头和说明，同时支持拖放；非空时添加与清空出现在标题区。选中内容或清单达到需要展开、搜索的规模时，才显示相应次级动作；次级工具行仅在排除、展开、移除或搜索有可见内容时占用高度，避免空行挤占清单。

搜索没有匹配时仍使用同一空状态操作入口，但点击只清除搜索并恢复清单，不打开添加面板。Mac 应采用同样的上下文语义：空草稿点击添加，搜索空结果点击恢复内容。展开清单只改变内容密度，不移动核心操作；排除编辑使用路径选择与原生面板，不增加第二套文件浏览器。

实现时让状态模型生成顶部动作的可见性、禁用原因和空状态操作类型，由 View 渲染；不要根据当前隐藏控件反推业务状态。文件区与设备区使用稳定分栏，工具区自适应内容高度、列表吸收剩余空间，避免操作出现或消失时整列跳动。

当前 Windows 设备行优先显示备注，原设备名主要在设备详情中查看；实际接收路径主要通过提示查看，来件清单只预览前 8 项。Mac 延续单行设备列表，补完整且可通过键盘打开的设备详情：备注、原名、平台、接收状态、分组、地址与指纹均可核查，信任和可连接状态分别解释。主界面与任务始终可查看真实保存路径，并提供完整来件清单入口；完成操作打开实际保存位置。

## macOS 原生工作台设计目标

[工作台静态设计图](assets/macos-workbench.png)随源码保存，便于在 Mac 本地继续参照。图中的文件、设备和路径为示例；发送草稿、单行设备项、设备详情及来件流程是后续界面目标，不能据此认定当前 Swift 功能已实现。

### 窗口与导航

建议默认主窗 1040×680 pt，最小 820×560 pt；侧栏约 180 至 220 pt，发送内容默认按 60:40 分配给文件和设备。这些尺寸是待实机验证的设计起点。分栏用 NavigationSplitView 或 HSplitView 配合原生侧栏样式，记住用户调整后的宽度。

侧栏保留“发送”与“传输记录”，未处理来件用数量徽标提示；接收规则、设备信任、通用和关于内容进入原生 Settings。主窗侧栏底部显示此设备名称、局域网连接状态、是否允许新接收与当前保存位置，路径提供“在 Finder 中显示”。局域网连接用于诊断网络与服务，暂停新接收只影响新请求，不把正在传输的任务混同为已停止。

使用系统标题栏与工具栏，避免大号品牌标题反复占用工作区。窗口可缩放、最小化与全屏；接收卡、任务详情和设置在更小窗口中可以滚动，不因固定高度截断按钮。

应用初期保留 Dock 与菜单栏入口。主窗关闭后仍可从 Dock、应用菜单和菜单栏恢复。主窗应使用可明确定位的单一 Window 场景及 openWindow 或专用窗口协调器；不通过 NSApp.windows.first 判断主窗，避免 Settings 或面板获得焦点后恢复错误窗口。场景与菜单栏入口参考 [Apple Window](https://developer.apple.com/documentation/swiftui/window) 和 [Apple MenuBarExtra](https://developer.apple.com/documentation/swiftui/menubarextra)。

### 发送内容区

顶部显示“待发送”、顶层项数和总大小。“添加”直接打开允许文件与文件夹混选的原生面板，减少先选类型的步骤；文件菜单可保留明确的文件或文件夹命令，作为辅助入口。文件区域支持 Finder 多项拖放，空状态的整块添加区域可聚焦、可点击，并有“拖入文件或文件夹，也可以点击添加”。

列表显示共享文件类型图标、名称、大小、目录内文件数量与扫描状态。文件信息按每项的实际字体测量完整名称和完整元数据；仅当“完整名称自然宽度 + 12 pt 间隔 + 完整元数据自然宽度”不超过可用文字区域时排成一行，名称在左、元数据组合靠右。元数据包含大小、数量及排除提示，不能先截断名称再判定为一行。文字区可用宽度先扣除图标、勾选、内边距和间距。

空间不足时保留两行：名称第一行，元数据第二行，垂直间距约 5 pt。两行模式下过长名称或统计仍可省略，完整路径和数值提供查看入口；排除数量保持可辨认。Windows 的 12 与 5 是逻辑尺寸，Mac 用系统字体和对应 point 尺寸重新校准，不复制像素宽度。

窗口或分栏缩放、侧栏变化、扫描结果、排除信息及本地化文字变化后重新测量；主清单与展开清单使用同一个布局组件，每项可独立采用一行或两行。目录统计异步进行；状态区分排队、扫描、完整统计、部分不可读与已排除。移除或重新加入同一路径后，旧扫描不得回写新项目。发送清单由传输层重新检查，显示的大小快照不能成为协议权威。

顶层项数与目录内文件数分开表达，例如“3 项 · 125 个文件 · 8 个文件夹 · 2.4 GB”。扫描未结束时显示“正在统计”，不要用暂时为零的大小暗示内容为空。目录默认折叠，展开查看相对路径；大量条目使用惰性列表与分页或按需展开。

添加、移除、清空、排除、展开和搜索入口放在顶部，移除只作用于选中顶层项。清空发送草稿不删除源文件。排除项只保存明确相对路径，沿用与 Windows 相同的目录排除语义，不独立引入 glob 语法。

说明默认折叠为简短入口，输入区打开后保持内容。辅助摘要在将来接入时明确标注，不替代真实清单；生成摘要是本机显式操作，不能因设备可信而自动执行。

### 文件、文件夹与平台图标

文件类型沿用当前软件的 32 类 Material 图标分类、原始几何与颜色。普通文件、PDF、Markdown、图片、压缩包、表格与代码类型保持跨端辨识；不再以通用线框图标或每台 Mac 默认关联应用的文件图标替代。分类按目录标记、特殊文件名和最后扩展名进行，大小写及两种路径分隔符与 Windows 一致；未知后缀回落到中性文件图标。分类不读取文件内容、不探测远端路径，不请求缩略图。

[共享图标目录与映射](assets/icons/catalog.json)已从实际软件图形导出：32 个原类型、一个 Mac 文件夹变体及三个平台标记，共 36 个 112×112 透明 PNG。[图标总览](assets/icons/contact-sheet.png)用于核对。现有 viewBox、nonzero 填充和多层颜色保留，详细来源与许可见 [文件图标说明](file-icons.md)。这些是设计及后续接入资源，当前 Swift 尚未引用。

普通文件夹是明确的平台外观例外。Mac 实现对已授权、实际存在的普通目录使用 NSWorkspace.icon(forFile:)；远端清单或已经失效的路径使用 NSWorkspace.icon(for: .folder) 获取当前系统的通用目录图标。保留系统颜色、渐变和内置阴影，不统一 tint、不重复增加阴影。当前 Windows 预览的 folder-macos.png 使用原有 folder-base 几何和蓝色代表这种差异，并非真实 Mac 系统图标截图。[Apple 路径图标](https://developer.apple.com/documentation/appkit/nsworkspace/icon(forfile:))、[Apple 类型图标](https://developer.apple.com/documentation/appkit/nsworkspace/icon(for:))

包目录保留独立 isPackage 语义；不能因为查询实际 .app 路径得到应用图标，就把普通目录传输误呈现为可运行应用或承诺包内容保真。包标记、符号链接与元数据限制仍按后文验收。

平台标记复用当前三类几何和映射：Windows 四格、macOS/mac/osx 笔记本、其他平台显示器；约 14 pt，以系统 secondary 颜色适配浅深外观。平台图标可按透明度作为 template 渲染，文件类型及系统文件夹保留 original 颜色。应用动作可以采用 SF Symbols，并配套文本标签；内容类型、平台身份与动作图标各自保持一致。

共享类型按 kind 缓存；通用系统文件夹独立缓存，实际目录按稳定 URL 或文件标识有界缓存，路径、自定义图标或授权变化时失效。不直接修改缓存 NSImage 的 size 或 isTemplate。icon(forFile:) 官方允许任意线程调用；界面发布与 AppKit view 更新仍在主线程，类型图标查询可采用有缓存的 MainActor 路由。Mac 本地资源验证完成前不能把 PNG 目录存在当作接入成功。[Apple original/template 渲染](https://developer.apple.com/documentation/swiftui/image/templaterenderingmode)

### 附近设备区

顶部工具栏保持一行：标题、分组菜单、显示数与总数、刷新。分组使用菜单替代当前三段选择器与额外分组行；菜单包含全部、与我同组、多组选和清除选择，已选分组可展开检查。

文本搜索匹配备注、原名、地址与分组。文本搜索只改变展示，保留已经选择的发送目标，同时显示“已选择的目标被搜索隐藏”及查看入口。分组筛选沿用当前安全语义：切换后清除被隐藏的目标，并即时反馈移除了哪些选择。二者分别定义，不能让用户误以为目标仍可见而意外发送。

设备项保持单行，依次呈现勾选、平台图标、备注或原设备名、受限状态图标和版本。名称占可伸缩空间并省略长文本，图标和版本保持可辨认；正常在线且允许接收时省略状态图标。暂停接收、可能离开和离线使用语义警示图标，帮助提示和 VoiceOver 读出具体原因，不把该图标当作信任标记。分组、信任和原名不常驻占行，完整信息进入设备详情。

勾选控制发送目标，详情通过设备名称入口、上下文菜单或键盘命令打开；两种动作明确区分，查看详情不改变选择。详情展示完整备注、原名、平台、运行版本、分组、接收状态、地址与可复制指纹。帮助提示提供快速查看，详情承担触控与键盘可达性，不能只依赖悬停。备注变化只影响显示，不改变指纹或自动分组来源。

当前 Swift 模型尚无应用版本与更新来源字段，也没有更新功能。P1 先添加可选版本字段的兼容解码，只以灰色显示对端实际报告的运行版本；未知版本不补造值，不显示蓝色更新动作。Windows 版本高于 Mac 0.1.0 不构成 Mac 更新资格。

蓝色入口在 P3 的 Mac 更新链路落地并验收后开放，显示适用更新目标版本，点击进入详情而非自动下载。来源必须在线、没有离开提示，版本与更新端点有效，且适用于 Mac 平台、架构和发行渠道；下载后仍验证固定发行信任根、包及文件完整性、app 签名与公证要求。设备信任不能替代发行验证。

列表稳定排序，避免周期广播导致行跳动。离线或发现过期要更新状态并在发送前重新检查；自动发现不向用户承诺对方永远在线。分组只影响展示，不停止后台发现或可信设备按既有规则接收。

设备数为零时区分可观测情况：服务尚未就绪、网络无可用接口、筛选无结果，或当前尚未发现设备。“未发现设备”不能直接显示“权限被拒绝”或“对方已离线”。空状态提供显示全部、刷新、网络诊断与通过 IP 连接入口。

手动 IP 是后续能力，当前 Mac 界面尚未实现。实现时只接受策略允许的数值局域网地址，显示目标证书身份与平台；它绕过发现障碍，不能绕过地址限制、指纹校验、接收确认或内容规则。

### 主发送动作

设备区底部保留一个主按钮，说明当前缺少内容、缺少目标、正在准备，或“发送给 2 台设备”。任务创建前重新验证文件清单和目标状态。发送开始后草稿保留并允许明确修改下一批内容；不能让正在传输的任务继续引用可变草稿。

多目标共享一次内容准备，每个目标拥有独立等待、进度与结果。用户取消一个目标时其他目标继续。未完成所有目标前不要把整批显示为“发送完成”。

## 接收与任务设计目标

### 来件确认

主窗显示轻量来件条和待确认数量；点击进入来件详情。窗口隐藏时菜单栏显示待确认徽标，可在获得通知许可后发系统通知，点击通知打开对应任务。通知是提醒，真实授权在来件详情中完成，避免通知内容缺失时接受不完整请求。

来件详情显示发送者备注与原名、身份状态、顶层项、文件和目录计数、准确总大小、发送说明、完整清单入口以及真实保存路径。目录清单按层级展开，大批次按需加载。完整 SHA-256 指纹支持选择、复制与逐段核对。

接受与拒绝始终可见；未知设备默认要求确认。当前 120 秒等待时间要在界面显示期限和过期状态。手动接受只授权当前请求，建立信任与自动接收使用独立操作。请求过期后按钮失效，点击不得生成过期许可。

确认后、写入前再次检查接收开关、设备身份、规则、路径权限、可用空间与目标冲突。不能把用户打开详情时的快照当成永久许可。失败显示具体原因并保留任务，允许更改保存位置后重新发起明确的接收流程。

### 任务状态与回执

任务模型至少包含以下阶段：排队、准备内容、等待对方确认、传输、校验、保存、完成、部分失败、已拒绝、已取消、已中断与回执未确认。发送与接收分别记录方向、目标指纹、批次、清单快照、时间、真实路径、规则原因和可执行操作。

“字节已经发送”与“对方确认校验并保存”是不同结果。发送端最终回执未收到时显示“回执未确认”，保留已知进度和核查入口，不直接宣告完成。接收端已经完成校验和保存，即使发送最终回执失败，接收任务仍是完成；两端各自保留准确的已知状态。哈希阶段和跨卷保存阶段使用独立进度文案，不能让百分比停在 100% 而长期没有解释。

任务列表提供进行中、待确认、已完成与失败筛选。活动任务显示速率、已传字节和可信的剩余时间估计；没有足够样本时不显示跳动的估计。完整错误保留在详情，短暂 toast 只承载“设置已保存”等反馈。

取消、拒绝、重试与继续区分语义。legacy 顺序流取消只保证本机取消行为，不能承诺远端已经删除临时文件或能从中断处继续。远端取消需实际实现并协商 receive-cancel-v1 后才宣告支持，校验取消方是原任务授权的证书身份；第三者不能取消别人的接收任务。重试旧协议意味着重新发送完整内容；只有双方协商块能力且恢复条件成立时才显示“继续”。

## 接收存储与恢复设计目标

当前 Mac 在临时目录接收整批，全部文件校验通过后移动成独立批次目录；接收或校验在提交前失败时不生成正式完成目录，提交后回执失败则保留完成目录。Windows 自 0.2.4 起已按文件校验并直接保存到确认目录，冲突自动追加序号。Mac 的后续储存改造需要显式决定新行为，并保留与旧任务的兼容，不能把当前整批提交描述成逐文件保存。

建议目标行为是逐文件验证后提交到已确认接收根目录。临时内容、块缓存与任务映射放在应用数据目录，完成后用户目录只保留实际文件和目录，不生成校验 JSON。已保存文件在后续中断或取消时保留，界面用“部分已保存”准确描述。

跨卷保存使用受控复制到目标卷的临时位置、校验、排他提交与清理流程，不假设 rename 或 move 在跨卷条件下具有相同原子性。禁止覆盖现有文件；空间不足、目标卷卸载或权限丢失时保留任务与明确错误。

同一顶层目录在批次内使用稳定的重名映射。例如接收 Photo 已有冲突而映射为 Photo (2)，后续文件都写入同一根目录；恢复时沿用已保存映射，不再次创建 Photo (3)。空目录也应映射并提交。映射与内容摘要、源身份及批次绑定，不能只根据文件名续写。

Finder 将 .app、.pages 等包目录呈现为一个项目，但底层仍有目录和文件。首版需要识别并标注包目录，验证展开与发送行为；不能从普通目录层级保真推导包文件可用、应用签名有效或元数据完整。带有符号链接和平台专有内容的包应按当前拒绝策略明确提示，相关兼容性单独验收。

继续保留路径穿越、符号链接、特殊文件、大小溢出、Windows 保留名、Unicode NFC 与大小写冲突检查。跨平台不能只按 Mac 文件系统规则校验。Finder 标签、资源分叉、ACL、硬链接与其他扩展属性当前不在保真承诺内；如果丢弃这些元数据，应在产品说明中清楚表达。

恢复依赖完整状态机、协议协商与持久任务，而不只是 UI 按钮。重启继续时重新检查源内容、身份、接收许可、目标映射与缓存摘要；取消和拒绝后清理可继续入口，清理失败在以后启动或接收时重试。

## 信任与设置设计目标

设备详情包含本机备注、对方原名、最后地址、公开分组、个人分组、完整证书指纹、身份信任与自动接收授权。个人分组只在本机生效，优先于对方公开分组；留空退回公开分组或原设备名前缀，备注不参与自动分组。

“已核对身份，信任此设备”与“允许匹配规则后自动接收”保持两个操作。指纹变化应建立新身份条目并显著提示，不按相同设备名继承信任。指纹继续是证书 DER 的 SHA-256，不能悄然改成公钥摘要。

分组名称遵循协议与现有实现的上限：自定义名称最多 80 个 UTF-16 代码单元，拒绝控制字符，去除首尾空白，匹配时忽略大小写。Swift 字符数量与 UTF-16 长度不同，表单验证必须与规则测试保持一致。

设置分为通用、接收规则、设备与信任、关于与更新；扩展能力在具备实现后再出现。通用显示设备名称、公开分组、默认过滤、接收目录、登录启动和本机身份。使用系统文件夹面板选择路径，并提供实际权限与可用状态。

规则列表按 first-match 顺序展示，支持拖动排序、启停、设备范围、内容范围、全部文件后缀、顶层目录模式、大小上限、目的地与自动接收。添加“用当前来件检查规则”预览，说明命中了哪条、为何不能自动接收及实际保存位置；预览不授予许可。

## 平台权限与原生生命周期

### 本地网络

Info.plist 已有 NSLocalNetworkUsageDescription。macOS 15 及以后对本地网络访问提供隐私权限控制；macOS 13 与 14 的验收应单独覆盖，不能把所有支持系统都描述成相同首次启动提示。权限触发与诊断依据 [Apple TN3179](https://developer.apple.com/documentation/technotes/tn3179-understanding-local-network-privacy)。

在真正开始本地网络操作的上下文解释用途，不反复触发请求。没有通用 API 可以直接查询所有本地网络权限状态；仅凭设备数为零不能判断拒绝。UI 应依据实际接口、网络操作错误和系统可观测结果提供诊断，并指导用户查看系统设置。

当前发现使用 UDP 子网广播，不使用 Bonjour 服务浏览。因此不要为现有实现虚构 NSBonjourServices 声明；日后采用 Bonjour 再按实际服务类型配置。也不要为 macOS 方案照搬 iOS 的 multicast entitlement。

### 文件与身份

保持 Keychain 中的 P-256 私钥和已持久身份，重启与升级不能不经说明生成新身份。身份初始化失败时显示持久错误，停止对外宣称可接收；提供诊断与明确的重置操作。重置身份意味着其他设备原信任失效。

当前构建不启用 App Sandbox。若后续采用 sandbox，接收目录和用户选择的源文件需要按实际授权使用 security-scoped bookmarks，启动时处理书签过期、卷离线与权限撤销；不能仅持久化路径字符串。相关系统行为见 [Apple 文件沙箱访问](https://developer.apple.com/documentation/security/accessing-files-from-the-macos-app-sandbox)。

登录启动继续使用 SMAppService.mainApp，界面呈现系统真实状态，包括等待用户批准或注册失败。只有应用确实可从 bundle 启动时才完成验收。菜单栏常驻不意味着后台 daemon，也不需要将默认应用升级成系统级服务，生命周期参考 [Apple SMAppService](https://developer.apple.com/documentation/servicemanagement/smappservice/mainapp)。

窗口隐藏后减少 UI 更新，网络仍采用异步等待与低频广播。用户设备正常唤醒、切换 Wi-Fi 或网卡变更后重建有效接口并重检连接；应用不承诺唤醒休眠设备或在睡眠期间继续传输。退出时若有活动任务，提供“完成后退出”“停止任务并退出”“返回”三个选择，明确处理待确认请求，再结束进程。

## 本地化与可访问性

首版提供简体中文与英文，使用 String Catalog 或 SwiftPM 可处理的本地化资源，避免把中文字符串继续散布在 View 与服务错误中。协议字段、指纹与日志代码保持稳定；界面通过状态和错误类型生成本地化文案。

文件、设备、目录与任务计数使用本地化复数形式；容量、日期和持续时间使用系统格式。路径和设备名按原值显示，支持长英文、中文、组合字符和从右到左文字；不要用字符串拼接固定计数语序。

VoiceOver 应读出设备备注、原名、接收状态、选择状态与信任状态。列表支持键盘多选和上下文菜单，拖放有添加面板替代入口，图标按钮具有文本名称。检查焦点顺序、禁用原因、提高对比度、深色模式和减少动态效果。

应用图标与文件类型图标保持不同用途；应用名称统一用 Boardcast，中文“邻间”作为辅助品牌名称。指纹和路径适合等宽或可选择文本，错误与状态说明使用正常正文宽度。

## 模块拆分与实现顺序

现有网络、身份、分组与规则文件保留独立职责。AppModel 逐步缩成组合入口，避免 SwiftUI View 直接创建连接、保存整个设置或操作临时文件。以下名称是模块职责建议，可按 SwiftPM target 与实际文件规模调整。

| 模块 | 职责 |
| --- | --- |
| AppState 与 WindowCoordinator | 主窗导航、可见性、打开指定任务、Dock 与菜单栏恢复 |
| SettingsStore 与 SettingsDraft | 持久化、迁移、草稿验证、即时设置命令与运行快照 |
| PeerStore 与 DiscoveryService | 发现状态、分组、搜索、稳定排序与选择策略 |
| SendDraft 与 SelectionScanner | 顶层内容、排除、目录统计与取消，生成不可变任务输入 |
| TransferCoordinator 与 TaskStore | 队列、每目标状态、来件许可、进度事件、历史与回执 |
| Identity 与 WireConnection | Keychain 身份、双向 TLS、帧限额、握手与能力协商 |
| ReceivePolicy 与 ReceiveStore | 规则决定、确认后重检、空间与路径检查、提交和冲突映射 |
| PlatformServices | 原生面板、Finder、系统文件夹图标、通知、登录项、书签与本地化资源 |

### P0 协议与可构建基线

在 Mac 上先跑 swift test 和通用 app 构建，修复 Swift 编译、SDK 可用性和资源装配。完成 Windows 与 Mac 的 discovery、hello、TLS、offer、确认、字节流与完成回执互通；特别检查双向证书、DER 指纹、消息字段和旧设备默认值。服务端必须显式要求对端证书，参考 [Apple TLS 身份验证](https://developer.apple.com/documentation/network/security-options)。

建立结构化错误和任务模型；发送开始及接收确认后重检身份、地址、许可、清单与保存位置。只对确实实现且通过互通验收的能力宣告 capabilities；尚未支持 chunks-v1 时走旧流式路径，不通过伪能力字段换取新 UI。

通过空文件、空目录、多级目录、指纹不一致、拒绝、确认超时、断网和同名内容的基础验收后，才扩大工作台功能。

### P1 原生工作台与本地化

完成发送草稿、Finder 拖放、顶部文件工具区、可点击空状态、双列与单行设备工具栏；增加搜索、目标选择、单行设备项、受限状态提示与完整设备详情入口、真实接收路径、完整来件清单和持久错误。

拆分设置草稿和即时偏好，完成原生菜单、快捷键、Dock 与菜单栏恢复。接入简中和英文资源、应用图标、共享类型图标资源与 Mac 文件夹样式，并完成浅深色、键盘与 VoiceOver 验收。多目标 UI 的开放以每目标任务模型和传输策略具备实现为前提；基础的多目标发送在本阶段共享一次枚举与内容准备，并使用独立连接和有界队列。

### P2 存储与恢复

实现逐文件提交、跨卷安全保存、稳定冲突映射、持久任务和缓存清理；随后对齐块协议、断点恢复与重启继续。接收部分成功、磁盘不足、卷离线和权限变更必须有准确任务结果。

用实际 Windows 0.2.7，并保留 0.2.4 兼容场景，与新旧 Mac 验收能力协商。旧协议始终保留明确的完整重试路径；新协议的继续入口以缓存校验和当前许可为条件。

### P3 Finder 集成与扩展

按真实需求加入 Finder Share Extension 或快速操作、CLI 与 stdio MCP；扩展只提交用户选择的文件，不扫描全盘。Share Extension 先做独立 target、签名、授权访问生命周期和向主应用移交文件的概念验证，再决定发行方式；明确扩展与主应用的 IPC、身份和文件权限边界。

基于块清单和已校验缓存的高级复用、LAN P2P 来源、更新分发及升级回滚在块传输和发行验证稳定后再落地。安装更新仍保留发布签名、公证与用户选择流程；来源设备可信不替代发行签名。QUIC、持续同步与系统 daemon 不作为本轮默认范围。

## Mac 本地构建与验收

当前脚本通过 swift test、arm64 与 x86_64 release 构建，将可执行文件和 Info.plist 放入 app，再签名和压缩。它尚未复制 SwiftPM 资源 bundle，也没有应用图标资源装配。引入本地化、图片或其他资源时，Package.swift、bundle 查找和构建脚本必须同步修改，验证从 dist/Boardcast.app 启动时也能定位资源。

本地验证入口：

~~~sh
cd platforms/macos
swift test
bash scripts/build.sh
open dist/Boardcast.app
~~~

默认 ad-hoc 签名供本机验证。对外分发应使用 Developer ID、Hardened Runtime 和公证，并验证 stapling 与 Gatekeeper；当前脚本不会自动申请证书或提交公证，流程参考 [Apple 公证与分发](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution)。最低 macOS 13，分别覆盖 Intel 与 Apple Silicon；资源和系统 API 的可用性以真实构建为准。

验收至少包含：

1. 同网段 Mac 与 Windows 双向发现、手动发送、接收暂停、分组过滤与旧设备缺省字段；手动 IP 在实现后单独验证。
2. 单文件、空文件、空目录、多级目录、大文件和大量小文件的内容及路径正确性，逐文件比较 SHA-256。
3. 未信任确认、已信任但未授权、规则不匹配、自动接收、指纹变化、拒绝与 120 秒过期。
4. 网络中断、休眠恢复、切换网络、服务启动失败与回执丢失；界面不得把失败或回执未知显示成完成。
5. 同名并发、大小写与 NFC 冲突、目标跨卷、磁盘不足、只读目录与卷卸载；符合当前版本承诺的部分保存和恢复行为。
6. macOS 13 与 14 的网络行为、macOS 15 及以后本地网络权限、Keychain、登录项、重启后身份和书签持久化。
7. 主窗关闭后恢复、Settings 打开时从菜单栏恢复主窗、多来件焦点、中文与英文长文案、深色与 VoiceOver。
8. 菜单栏空闲 30 分钟的 CPU、RSS 与唤醒次数，分别记录大文件与大量小文件的速度和准备时间；实体局域网测试与回环测试分别报告。

文档和界面按实际状态区分未实现能力与已实现但待验收能力，只有 Mac 本地构建和双机验收通过后才更新对应承诺。文件行另验收临界宽度、宽→窄→宽、统计与排除改变后的双向切换、主清单与展开一致；图标另验收分类、透明边缘、浅深外观、显示缩放、包目录与移动 app 后资源定位。项目级操作入口与构建约定见 [开发说明](../platforms/macos/DEVELOPMENT.md)，本页作为实现和后续设计调整的持续基线。
