# P2P 分发调研与调度设计

调研日期：2026-10-09（Asia/Shanghai）。所有链接均在该日查阅。

本文区分官方已公开的行为、本项目的工程推论和建议参数。本文不是吞吐量基准；未对多台真实设备、有线交换机或 Wi-Fi 完成性能验收。参数必须通过文末矩阵验证，不能据此承诺倍速。

## 1. Steam 的经验：有条件的局域网文件复用

Valve 官方描述的 Local Network Game Transfers 是从同一 LAN 上已有内容的 Steam 客户端复制游戏安装或更新文件；参与双方需要允许传输，发送端须处于空闲等合适状态。内容不可用或连接中断后，接收端转向 Steam 内容服务器取得剩余数据。收到的内容会验证，损坏内容不会安装。[Valve：Steam Local Network Game Transfers](https://help.steampowered.com/en/faqs/view/46BD-6BA8-B012-CE43)

这证明的是“发现已有副本、满足条件后直传、保留主源回退”。该文没有公布同时从任意多个 LAN 客户端下载的 swarm 调度，也没有公布最佳 peer 数或文件大小门槛，因此不能把 Boardcast 的多接收端分块转发称为“Steam 同款 P2P 算法”。官方页面中的有线吞吐示例也不是本项目性能指标。

SteamPipe 将文件划分成约 1 MB 块，更新时尝试复用旧版本匹配块，只下载需要的新块；包文件布局变化会放大下载或本地磁盘工作量。[Valve：Uploading to Steam / Game Content Structure](https://partner.steamgames.com/doc/sdk/uploading?l=english)

对 Boardcast 的工程启发：更新包就是带版本、平台及可信校验信息的文件。版本发现与内容传输分离；用户选择版本之后，交给同一分块清单、缓存、校验、断点恢复和进度流程。不要因为更新入口不同再实现第二套传输引擎。SteamPipe 的跨版本差分能力并不意味着现有完整 ZIP 包天然能获得同样的差分收益。

## 3. 对现有实现的具体判断

调研起点的 `TransferChunkProtocol.cs` 以 `ChunkIndex % 3` 固定安排约三分之二请求优先尝试中继，其余去原始发送端。它没有依据总大小、已知可用块、近期速率或服务端负载决定比例；中继请求失败后会回退，但一次尝试可先占用约 3 秒。多个接收端以相同顺序读取内容时，还可能频繁碰到未下载的块。

因此“握手支持分块”不应直接等价于“启用 P2P”。分块协议本身应继续用于单接收端和小文件，保留恢复与校验；需要按条件开启的是额外的 peer 连接与分担上传。

优先复用现有 `ChunkManifest`、`ChunkStore`、SHA-256 校验、TLS 设备身份与按批次签发的接收者授权。保留每个来源的统计即可改善策略，无需替换底层协议栈或接入公共 DHT。

## 4. 本次实际实现

下表根据本次代码 `ChunkPeerPolicy.cs`、`TransferChunkProtocol.cs` 和 `PeerUpdateService.cs` 核对。它与下一节的进一步建议分开：门槛是保守默认值，未经过真实 LAN 参数寻优。

| 项目 | 本次实现 |
| --- | --- |
| 共用传输核心 | 普通文件与所选更新包复用 `ChunkManifest`、`ChunkStore`、`ChunkTransfer.DownloadAsync` 和 `ChunkPeerPolicy`；更新保留专有发行签名、完整包及安装前校验。 |
| 内容规模 | 普通文件按总内容、更新包按此次开始时未完成内容计算，至少 64 MiB 才考虑加速。更小内容仍走分块／校验／恢复，只是不额外探测 peers。 |
| 普通文件的额外条件 | 原始发送端当前同时服务至少 2 个该批接收会话；候选上报的已验证内容至少为 2 个清单块；当前块至少 256 KiB，任务剩余至少 8 MiB。一个接收者、小块和尾部默认由原始发送端直传。 |
| 更新包的额外条件 | 主源实测移动平均低于 32 MiB/s、当前块至少 256 KiB、动态剩余至少 8 MiB 时才考虑备选设备；主源失败时允许绕过加速门槛寻找同一已验证包，属于恢复回退。 |
| 主源基线 | 至少 2 个成功主源块样本；移动平均权重为新样本 0.25、旧值 0.75。清单真实块大小传入策略，支持 1–8 MiB 块。 |
| 来源准入 | 至多 1 个未知 peer 探测同时在途；单个来源最多 1 个请求在途。成功返回并校验的样本速率和该源移动平均都达到同期主源的 80%，才保留该来源。首版不是“必须 2 次 peer 成功”。 |
| 超时 | peer 块探测根据块大小与主源速率计算，限制在 2–10 秒。更新候选连接另有 5 秒上限，最多 2 个延迟连接的候选，不在主源数据传输前逐个连接。 |
| 退避及隔离 | 策略失败或慢源冷却为 30、60、120、240 秒，之后封顶 300 秒；计时使用单调时钟。普通文件 SHA-256 错误在本次任务中隔离该中继。更新下载对连接／读块异常的候选在本次任务中直接排除，手动恢复可重新选择来源。 |
| 上传负载 | 普通文件整机最多 2 个活跃中继会话，超额请求立即拒绝；这是并发上限，不是 CPU／磁盘空闲检测。 |
| 测速边界 | 普通文件计量实际块请求、读取及校验，不把首次 TLS 连接时间混入稳态吞吐。更新首次候选样本包含候选连接成本，是更保守的准入。 |
| 主源通道 | 普通文件保留周期性主源块请求以刷新来源与吞吐基线；其他块只有通过准入才尝试 peer，不再无条件安排固定比例中继。 |
| 可用性元数据 | 普通文件分享的是该来源的已验证总字节，尚不是逐块位图；缺块时立即回主源。它只能用于候选筛选，不能证明某个请求块已存在。 |

**尚未实现的观测能力：** 当前没有“接入 peer 前后总吞吐”的 5–10 秒比较窗口，也没有整机 CPU／磁盘忙闲采样，因此不能描述为已基于总吞吐自动寻找最优 peer 数。80% 比率是来源级保护，不能单独证明全批完成时间缩短。完整 availability 位图、rarest-first 和重复请求取消同样不是本次实现。

## 5. 工程建议与后续优化

本节保留研究阶段的建议，用于后续评估；其中未列入上一节的能力不能视为已经实现。数值不是 Valve、Microsoft 或 BitTorrent 的性能结论。实际首版参数以上一节和代码为准。

### 5.1 候选条件

1. 用户已发起该批文件传输，或已明确选定要取得的更新版本。版本发现不拉取更新包。
2. 接收方支持分块协议；普通文件同批至少存在另一个已批准的接收方，单接收端默认直传。更新可在已有相同可信包的设备之间择源，但仍应先衡量主源是否足够快。
3. 未完成内容足够大：初始建议总内容至少 64 MiB，且有多个可复用块。64 MiB 借鉴“设置下限”的思路，不等同于 Windows 默认 50 MB。
4. 候选设备在现有 LAN 地址约束内，TLS 指纹匹配；原始发送端为当前批次和内容签发的授权仍有效。发现到设备不等于获得内容访问授权。
5. 优先选择已确认持有所需验证块的设备；若首版仅有批次来源列表，缺块响应必须轻量并立即回退，不能长时间排队等它下载。

大批微小文件应特别谨慎：即使总量超过门槛，每次 peer 请求的有用数据仍可能很少。本次普通文件已增加最小块长度与剩余量限制；后续可继续评估平均文件大小与实际请求开销，不要用“总文件数很多”作为加速证据。

### 5.2 不阻塞主源的试用与保留条件

- 从原始发送端立即取得数据。初始建议至少取得 4 个有效块再对主源速度形成基线，测速计入真实读取／校验耗时；主源排队耗时另外记录，避免把本机锁等待误认为网络慢。
- 初次最多探测一个 peer，最多一个在途块。主源保持进展。未知节点的探测预算要有限，不能遍历 32 个来源各等一次超时。
- 以“验证后有用字节 / 耗时”的移动平均比较来源，而非网卡标称速率。建议起始准入线为 peer 达到同期主源的约 80%，配合至少 2 次成功样本；该值保守地避免较慢节点长期拖尾。
- peer 的单块速率合格并不证明总吞吐提升。可实现接收端 5–10 秒观测窗，比较接入前的主源基线与接入后的总验证吞吐；连续两个窗口无收益或退化时缩减／暂停 peer，保留迟滞防止抖动。
- 初始建议每个接收任务至多 2 个 peer 在途请求，整机中继服务最多 2 个活跃会话；主源通道保留。达到上限时快速返回 busy，不能无限等待上传槽位。
- 若暂未实现整机 CPU／磁盘利用率采样，应明确仅通过并发上限与真实请求耗时限制负载，不把“存在两个空槽位”描述为“设备空闲”。

原始发送端上行受限而其他链路有余量时，中继可能降低原始发送端重复发送的总量；原始发送端本已足够快、接收磁盘饱和或所有设备共用拥塞 Wi-Fi 时，增加中继未必缩短完成时间。尤其不要以 peer 字节比例高作为提速成立的证据。

### 5.3 缺块、慢源与失败

| 结果 | 建议行为 |
| --- | --- |
| `chunk-missing` | 当前块立即回原始发送端；短暂冷却该来源或该块，不立刻重复请求；不视为校验攻击。 |
| busy／服务槽满 | 当前块立即回主源，数秒后才有限探测；避免把对方排队时间计成成功吞吐。 |
| 连接失败／超时／中断 | 释放连接；当前块回主源；按连续失败次数退避，例如 3、6、12、24 秒，封顶 30 秒并可加少量抖动。 |
| 哈希不匹配／身份或授权错误 | 不写入／不转发该数据；本次传输隔离该来源，回主源取得同一块；记录可定位诊断。 |
| 测速无收益 | 暂停 peer 一段观测周期，主源继续；以后最多一次轻量试用，不每块重试。 |
| 主源或所有有效源暂时离线 | 保留验证过的块与任务状态；恢复后只请求缺失块，不能因为 peer 失败清空缓存。 |

现有顺序请求协议若缺少取消在途块的机制，尾部阶段应减少新的慢 peer 请求并缩短合理超时；不要为模仿 BitTorrent endgame 而对所有来源重复下载所有剩余块。真正的竞争请求需要取消、去重、准确流量统计和额外协议测试。

## 6. 更新与普通文件共用的边界

- 版本目录／设备广播只包含版本、平台、包大小、可信散列或清单标识等元数据。探测版本不等于自动下载。
- 用户选择版本之后，将不可变更新包作为普通内容任务进入现有传输引擎；直接来源、验证缓存和候选 peers 都通过同一个内容身份识别。
- 更新包来源选择服从同样的门槛和速率策略。只有一台设备持有所选版本时，从该设备直传已经满足需求，无需刻意制造 swarm。
- 更新包完整性和版本／平台适配校验仍是安装边界的一部分；传输完成不意味着立即替换运行文件。不可把网络发现的任意 ZIP 当作可信可执行更新。
- 首版不必实现公共互联网 P2P、NAT 穿透、跨批次全局分享、跨版本二进制差分、自动预下载。它们不属于满足本次局域网传输恢复与按需更新所必需的范围。

## 7. 如何证明有效

功能自动测试可以验证门槛和回退；真实性能必须用代表性的多机网络比较。至少记录：每接收端完成时间、全批最后完成时间、主源上传字节、peer 有效字节、重试／缺块次数、峰值中继会话数，以及磁盘或 CPU 是否已成为瓶颈。

| 场景 | 需要验证的结果 |
| --- | --- |
| 1 MiB／32 MiB，小文件，1 或多接收端 | 不开启额外 peer 连接；直传、哈希与恢复仍可用。 |
| 256 MiB／1 GiB，单接收端 | 直传，额外调度开销接近零。 |
| 大文件，2–4 接收端，有线，限制原始发送端上行 | peer 可承载有效字节；与禁用 peers 的同条件基线比较批次完成时间和主源字节。 |
| 大文件，多接收端，同一 Wi-Fi | 不预设收益；无益时策略应停止扩大 peer 使用。 |
| 慢盘、慢 peer、missing、busy、随机断连 | 主源继续推进；无无限重试；并发始终有界。 |
| 伪造或损坏块、错误授权 | 数据不落为已验证块；来源隔离；正确主源可以补足。 |
| 接收或发送进程重启、确认消息丢失 | 只复用重新验证的缓存；完成目录不会重复提交。 |
| 更新版本探测后不选择；选择后中断再恢复 | 探测无包下载；选择后的更新任务复用文件传输与缓存。 |

同一场景至少重复数轮，记录版本、网络拓扑、文件大小、缓存冷／热状态和机器配置。若只做了单机 loopback 集成测试，应报告“协议、恢复与退避验证通过”，不能报告“LAN 已提速”。
