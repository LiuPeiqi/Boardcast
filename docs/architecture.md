# 工程取舍

## 目标和边界

Boardcast 只做局域网点对点传送。优化目标按顺序为：后台空闲开销低、传输内存有界、文件正确性、易用、易分发。不存在公网发现、云中继、P2P 打洞、远程服务或默认上传遥测。设备地址与传输端点在建立连接前检查。

网络可达性、磁盘、Wi-Fi 和 TLS 加密都会影响吞吐；不能用回环测试证明能跑满某种局域网带宽。没有实测的资源和性能指标不做保证。

## Windows 进程拆分

`Boardcast.exe` 是 C# / WPF 原生窗口。关闭按钮隐藏窗口到原生 Windows 系统托盘，保留当前选择与界面状态；隐藏期间停止界面轮询，网络来件通过窗口消息按需唤回，不增加后台轮询。托盘右键退出会取消本机摘要任务，通过当前用户管道请求停止后台，并确认对应后台进程结束后退出 WPF。托盘图标使用 Shell_NotifyIcon，不引入 WinForms 或额外运行时。

`Boardcast.Daemon.exe` 使用 .NET 基础库承载网络，无 ASP.NET 服务栈、浏览器内核或第三方运行时。异步等待 socket/pipe，低频发现，不扫整个网段。接收内容先检查清单和许可，再分配传输资源。

`boardcast-cli.exe` 使用同一受当前用户保护的本地 IPC，向脚本和 LLM 暴露命令行/stdio MCP。

默认部署为用户会话后台，登录启动是显式选项。它不能在用户退出登录后继续代该用户弹确认窗口。Windows 的服务会话隔离意味着系统服务不能直接作为交互 UI；参考 [Microsoft Interactive Services](https://learn.microsoft.com/en-us/windows/win32/services/interactive-services)。

## 为什么使用 C# / WPF

这是针对 Windows 主平台的工程选择，不是跨平台 UI 折中。WPF 有原生文件对话框、键盘导航、DPI 与 Windows 桌面生态；网络核心使用成熟的 Schannel/TLS 和 socket 封装。本机 SDK 可直接构建验证，项目不依赖外部 NuGet 包。

Rust/Win32 在小体积、无 GC 常驻程序上有潜在优势，但需要更大范围的 Win32 和 UI 工程。没有同功能基准，不能宣称 C# 最省内存。当前先通过界面/后台拆分和有界缓冲控制开销，并公开实测。Native AOT 是后续可评估方案，不能把本版普通发布误称为 AOT。

[Microsoft 发布说明](https://learn.microsoft.com/en-us/dotnet/core/deploying/)支持自包含分发；它避免用户额外安装运行时，但增大发行包。我们接受这一明确的体积取舍。

## 内容选择与目录统计

发送区的“添加”菜单分别调用 Windows 的 OpenFileDialog / OpenFolderDialog，支持系统多选和直接拖入，不实现自己的文件浏览器。文件与文件夹进入同一发送列表；已移除旧自制浏览器及其导航、枚举和选择状态代码。

只有加入发送队列的目录才递归统计。共享 SemaphoreSlim 将扫描并发限制为 `clamp(CPU / 2, 1, 4)`；先异步获取槽位，再交给线程池，排队不占工作线程。统计只读文件元数据，按目录深度保留枚举器，取消时释放。每个选择项独立持有取消令牌，移除后禁止旧任务回写，重加同一路径或修改排除项创建新任务，旧令牌的结果不能回写。退出时取消扫描并等待清理；系统正在处理的单次文件系统调用返回后才可响应协作取消。

每个源文件夹可保存一组明确的子项相对路径。TransferExclusions 负责规范化和整目录排除，大小扫描、发送清单和摘要共用该语义。排除项编辑复用现有 EditorDialog 和系统选择器，不增加 glob 引擎或第二套浏览器。

大小是选择后的快照；跳过链接或不可读项目时明确显示不完整。发送清单仍由传输层重新构建，不把界面统计作为传输内容的权威依据。

## 传输路径

Windows 的普通文件和更新包共用 `ChunkTransfer` / `ChunkStore`：清单包含独立 SHA-256 分块，接收端只请求缺失或重新校验失败的块，完整校验后提交。分块默认 1 MiB，清单过大时增至最多 8 MiB；内存与工作并发有界。新文件连接通过 `chunks-v1` 能力协商启用，旧设备继续使用按清单顺序的 TLS 字节流。为了得到稳定内容标识，新路径在发送前读取源内容生成块摘要；多目标共享这一次准备。普通文件不默认压缩，也不预先打包 ZIP。

[LocalSend 协议](https://github.com/localsend/protocol)展示了本地发现、证书身份和分阶段接收的可行性。Boardcast 借鉴这种分离；自身协议优先局域网长连接和目录保真，不实现协议兼容。

[Syncthing 同步说明](https://docs.syncthing.net/users/syncing.html)说明块哈希可支持同步重用。本软件仍是一次性发送工具，不引入全盘索引和持续目录扫描。当前实现保留中断任务和已验证的接收内容，用户可在重启后继续；继续时重新检查源文件、接收许可及缓存摘要。显式取消删除本机恢复任务，拒绝或完成也不再保留可继续入口。Windows 0.2.4 接收端按文件校验并直接保存到确认的目录；重名自动追加序号。分块与完成映射存放在设备自己的应用数据目录，完成后不留下用户可见的校验 JSON 或任务目录。取消只清理未完成内容，保留已保存的文件；中断保留有效进度，删除失败在后台启动和后续接收时重试。旧协议设备只能重新发送完整文件。

同一批次的 LAN P2P 只在大文件、多接收方竞争以及候选已有校验块等条件满足后尝试。原发送者的签名授权绑定批次、内容和接收证书指纹；中继只提供该批次已校验的块，失败回到原发送者。调度根据实测速率停用较慢来源，并限制试探和退避。更新包复用相同的块引擎及来源策略，但保留发行签名和安装验证：用户先选版本，才启动传输；只探测版本不会自动下载。实现和阈值见[多设备传输](multi-recipient-transfer.md)、[更新流程](peer-updates.md)与[P2P 研究](p2p-distribution-research.md)。

## macOS

现有独立 Swift / SwiftUI、Network.framework、Security、CryptoKit 源码不依赖 .NET 或共享 WPF 代码。本轮不扩展 macOS，也不声称其已支持 Windows 0.2.2 的块传输、恢复、P2P 与更新；后续在 Mac 上构建并按能力协商验证互通。平台专有文件元数据不应被默默当作跨平台已保留内容。后续原生工作台、状态模型与能力迁移见 [macOS 产品设计](macos-design.md)，本地构建与分阶段验收见 [Mac 开发交接](../platforms/macos/DEVELOPMENT.md)；新增设计尚未改变当前 Swift 功能。

## 扩展边界

CLI 运行必须从本机显式操作发起，远端只能提交描述性文本，不提供可执行钩子。MCP 是标准输入输出协议，不绑定网络端口。自动接收文件不是自动授权执行该文件，也不是向第三方服务外发内容的授权。

## 暂缓范围

本轮不实现文件组播、QUIC、Wake-on-LAN、全盘内容去重或持续同步。可靠组播还需要拥塞、丢包修复及群组授权；QUIC 不会单独解决来源选择和慢盘瓶颈。当前保留普通字节与目录层级，不承诺 ACL、NTFS ADS、硬链接、Finder 标签或资源分叉保真。正式发行私钥、Windows 代码签名证书、实体多机速度与干净环境安装验收仍由后续发布流程完成；本机回环测试不能代替它们。
